# CleanRooms Studio

A planning and employee demo hosted on Sites with Vinext and Cloudflare D1. The original visualization iframe sandbox and both CSPs are preserved exactly. A narrowly scoped same-origin transport iframe lets the sandboxed application save through the authenticated API.

Run `npm ci`, `npm test`, then `npm run build`. The prebuild regenerates `site/index.html` from `src/` and builds the rich editor locally. Vinext emits the Worker in `dist/`. Run `npm run dev` for local preview; the supplied Sites local sign-in is development-only. Apply generated migrations to local D1 as described in the Sites starter before exercising persistence locally.

`/api/studio` requires Sites identity and resolves a server-owned workspace membership. Draft shifts, series and week caches have independent D1 records and versions. Employees, worksites and departments have separate directory records and versions. A workspace revision still fences atomic multi-record plan changes; member preferences are separate and saved atomically with permitted plan writes. Existing authenticated snapshot owners bootstrap as immutable workspace owners. Unknown visitors need an invitation; there is no first-visitor signup. The current Site remains owner-private. The employee picker is available only to users who may plan and remains an explicit preview of the published plan.

Optional instructions use backward-compatible plain `note` and canonical JSON-string `noteRich`. The model allowlists structure, formatting and safe links and renders with DOM text nodes. Untouched legacy text remains exact; there is no low text-length cap. Requests have a16MiB bound and report storage failures visibly.

`checklistProgress` stores completion by concrete shift ID and assignee, independently of the unchecked instruction template. Matching task signatures preserve progress through moves and unrelated edits; copies and new series occurrences start fresh. Changed task text resets that task, changed list topology resets the occurrence, and reassignment removes the previous assignee's progress. Completion never changes plan-publication diffs. Planner undo retains later completion updates for unchanged tasks. Demo entry/reset/exit isolates and restores progress with the plan.

The administrator's editor preview still has disposable local checkboxes. Saved employee completion is displayed separately on the administrator's shift editor. Server save receipts determine the employee's saved status; conflicts offer an explicit refresh instead of silently overwriting another window.

The employee overview defaults to a monthly calendar, with week/day views and one shared focus date. Its published-only calendar loads one selected person and date window through `employeeRead`; long instructions and checklist structure load through the point operation `employeeShift` only when a shift is opened. Calendar rows carry compact completion totals. The initial employee response uses the same scoped projection, and late period/detail responses cannot replace a newer selection. View/date preferences and the existing modal drawer remain unchanged.

The Vagtplan header has a searchable department switcher. A department is a branch or customer grouping of one or more worksites; a worksite may appear in multiple groups. Administrators of their own saved plan can create/edit these groups and append worksites with addresses. Numeric worksite indices remain stable for existing shifts, series and coverage rules. Department selection scopes the planning calendar, worksite filter and new-shift default; staffing conflicts, drift review and week publication still cover the entire plan and are labeled accordingly. Employee calendars continue to show all of that person's shifts.

Department management uses workspace-owned role definitions. The enforced permission catalog is `plan`, `departments.manage`, `users.manage`, `roles.manage`, `payroll.view`, `payroll.manage` and `payroll.groups.manage`; department management requires planning access. Roles can be named, created, edited and assigned to accounts or invitations. Immutable standard roles preserve existing access; the owner remains bound to the protected Administrator role. Users may only create, edit or assign roles whose permissions fit within their own authority. Accounts/role managers without planning permission receive no complete plan; bound staff can still access their own effective assignments and checklist progress.

Administrators set the GPS requirement, center and radius per worksite under Indstillinger → Arbejdssteder. A worksite's current versioned settings apply at web clock-in, even to already published shifts. GPS is off by default; switching it off keeps the configured center and radius. The authenticated timekeeping endpoint validates the one-time browser position when required and does not store it in attendance or activity history. Browser positions are client-provided and are not device attestation. The standalone native demo uses its own local fixtures.

Every mutation rechecks membership and the live role version. Role edits atomically update the definition, refresh derived compatibility fields, bump assignee versions and revoke invitations issued by members who lose account-management permission. Active staff bindings remain unique; an empty-permission role requires a staff binding. Snapshot and account SQL commits fence stale member/role contexts, including role-definition changes while a write is in flight. Legacy role columns are compatibility data after roleId adoption and never override the definition. A user without department permission must preserve organization data exactly. Personal checklist writes resolve the bound staff identity and current occurrence on the server, and conflicts never expose a full snapshot to an account without planning permission.

`/api/accounts` provides guarded member edits, soft deactivation, expiring one-time invitations, personal preferences and narrow employee checklist mutations. Invitation secrets are random, stored only as hashes, bound to the invited email and accepted once by a signed-in Sites identity. Pending invitations can be revoked; demoting/deactivating their issuing admin also revokes them. The immutable workspace owner prevents administrator lockout, and an active employee can have only one bound account. Invitation links are copied and shared by the administrator; the app sends no email. `/join` uses a separate nonce CSP and top-level Sites sign-in.

Application membership does not change the Sites hosting audience. Invitees must also have permission to visit the private Site; no audience or visitor grants are changed automatically by this implementation. One workspace per account is supported.


## Persistence boundaries

Planning uses `workspace_plan_records` for independently versioned series, shift overrides/suppressions and week caches. Published assignments, publication scopes and publication history have separate authoritative records. The remaining revisioned snapshot holds shared metadata and a compatible projection is reconstructed for the existing UI. Operational writes are independent: attendance uses `workspace_time_entries`, checklist tasks use `workspace_checklist_tasks`, shift requests/messages use their own tables, and absence requests use `workspace_absences`. Plan publication is atomic with its messages and applicable attendance/absence guards. Personal payroll revisions and account administration have durable histories. Approval keeps a frozen salary receipt.

Modern clients submit changed records with their loaded versions, rather than resending all shifts and series. Disjoint draft changes can merge across a newer workspace revision. A changed target, parent series or affected series group produces a conflict; tombstones retain versions across deletion and recreation. Publication still requires the exact reviewed workspace revision. Save receipts describe the writer's own commit, and queued edits, open editors and undo preserve that causal boundary. Legacy clients retain strict whole-plan revision checks.

The planner calendar bootstraps one week, measures visible week sections in its own scroll container and requests those weeks plus one adjacent prefetch week through revision-pinned pages with `instructions=deferred`. The existing eight-week layout, zoom, filters and day list remain unchanged. A bounded weekly cache normally retains four weeks and can retain up to eight when the visible/selected working range requires them. Only missing complete weeks are fetched; evicted weeks keep measured heights and neutral loading placeholders. Cache generations include the plan, directory, absence revision, tenant and viewer authority; failures or superseded reads preserve the active model. Shared long-running series are expanded only inside loaded weeks, and unloaded weeks never display inferred shifts or false zero totals. Draft schedules, published comparison rows and week baselines carry compact instruction tokens rather than description bodies or checklist structure/progress. Opening a shift calls `plannerDetail` for the selected occurrence and its required parent/override records. Moving, copying and bulk editing cross the same hydration barrier before capture or mutation. Unloaded instructions are distinct from empty instructions; the client blocks unhydrated writes and the server rejects read-model markers in write commands. Point reads preserve the observed plan/directory generations and update the acknowledged baseline without creating a draft edit. Indexed candidates still include actual/original occurrence dates and complete calendar absence coverage. Missing records outside the window are never treated as deletions.

Scroll reads coalesce missing weeks into batches of at most two weeks. At most one newly fetched read-ahead week may sit beyond the requested visible/neighbor range, within the existing eight-week display bounds. Complete batches split into exact weekly cache entries using version-fenced index geometry; only the requested range becomes editable authority. A completed obsolete scroll batch may warm the private cache in the same unchanged context, but cannot replace the active model. Navigation, editor and selection changes stop pagination. Oversized batches fall back to required single weeks, and older receipts without geometry retain the single-week path.

Calendar remounts restore their date anchor synchronously once measurable, so consecutive data renders cannot capture an intermediate position. New scrolling overrides a deferred restoration, and scroll direction survives remounts without treating layout compensation as user movement. When the visible/selected weeks are already cached, the planner adopts them through the normal version-checked viewport path before waiting for a missing neighbor. Cache hints never grant editable authority; a failed neighbor read preserves the visible weeks.

Ordinary data/loading updates retain the same calendar scroll element and observer. Only changed weeks are patched; unchanged cards and days retain their DOM identity, and loading status is limited to the requested weeks. Observed week heights survive eviction/reload, with explicit expansion/collapse allowed to resize. An in-place patch compensates only actual height changes above the current date; no-op updates never assign scrollTop. Kept handlers resolve the latest occurrence and callbacks, while detached controls cannot act on the plan.

After the visible calendar is ready, the app warms a six-week window within its eight-week display bounds. At most two weeks are collected per background batch, with one background request in flight; foreground reads, edits and saves preempt further collection. Warming upgrades private retention to at most twelve compact weeks while retaining the 64 MiB byte budget, so moving the six-week warm window does not immediately evict recently visited weeks. It does not expand editable authority or show a loading overlay. Verified detail reads and same-generation series/publication reads preserve compact week entries, including matching absence coverage. The first bootstrap still loads one week.

Planner point details have a separate 100-selection/8 MiB LRU. A matching generation, record versions and instruction tokens permit local reuse; progress snapshots expire after 30 seconds and are scoped to the concrete occurrence/person. Hits do not extend their freshness, and own checklist changes invalidate progress and outstanding older detail replies. Larger descriptions still open intact without entering this cache. First-use details show feedback on the selected card, while full-page loading is reserved for account bootstrap; scope reads retain edit guards and a small header indicator. A newer user action cancels the older detail-opening intent.

Series-wide editing loads the complete selected agreement, including distant exceptions and tombstone versions, alongside compact read-only schedules for the affected weeks. The series list uses compact summaries without instruction bodies. Publication review loads only the selected periods and worksites plus the transitive dependencies of moved shifts. Their background calendar remains compact. Returning to the calendar releases operation projections and loaded instruction bodies. Pure view/preference changes do not write or advance the plan revision.

Deferred calendar pages allow up to 1,000 selected rows with the existing soft 1 MiB payload budget; legacy and operation pages retain their 500-row ceiling. An existing long description stays intact, and the collector fails explicitly if the complete window exceeds its 64 MiB/50,000-record working-set limit. It never silently truncates the period. The first request after upgrade may perform a one-time source-fenced index/import transition. Normal calendar reads omit unrelated payloads and publication history. Modern clients opt into targeted command writes with exact record-patch receipts. Save reads cover changed keys and their required parent/group dependencies; publication reads cover its server-expanded scope closure and compact conflict neighbors. Neither write path reloads the background calendar. Legacy clients and shared-metadata administration retain the compatible full-context path.

Existing snapshot/attendance data is imported idempotently under live ACL and source-version guards. Draft and publication imports commit together with their completion marker. Imports do not silently discard the original data after a failed migration. Long instructions use bounded UTF-8 chunks with integrity checks. Attendance history is archived before the schema-1 ledger becomes a small schema-2 header. New migrations are additive; applied migration files remain immutable.

`leaveRead` is a scoped, filtered cursor API. `leaveCreate` binds an employee to their own account; planners may choose a roster person. `leaveDecide` requires a current request version, with a mandatory rejection reason. The three old examples are imported once for matching demo identities; real requests are stored records. Normal plan saves cannot overwrite real absence decisions. Demo decisions remain local to the demo.

Time reads have row and byte bounds and return `nextCursor` plus ledger, plan and directory generations; clients restart if a multi-page load crosses versions. Warm Timer requests select attendance and compact published schedules for the requested period/person, plus the matching draft summaries for the weekly overview. Payroll estimates fetch personal agreements only for the affected employees. Fravær queries return only matching requests and their compact employee labels. Neither page requires a full planning snapshot; cold legacy imports and summary repair remain explicit upgrade paths. An approved or submitted registration retains its original assignee and plan even if a shift is later cancelled. Publication cannot reassign/date-move a registered occurrence or cancel a running occurrence. Ambiguous DST work can be closed safely, but requires an explicit, reasoned UTC correction before approval. Planned breaks are unpaid and the estimate allocates them at the end of the shift; that calculation assumption is visible in the UI.

`/api/directory` reads employee profiles by ID and pages compact directory catalogs. Employee, worksite and department edits patch only known editable fields with the loaded entity version. Unknown profile fields remain intact. Directory commits have an independent generation and do not advance the plan revision; plan publication checks the reviewed directory generation. Existing snapshot aliases are removed only after a source-fenced import succeeds. Stable worksite indices preserve all existing shift references. Employee lists use a bounded upcoming plan window and profiles load the selected month.

Messages and shift requests use generation-pinned pages and load only referenced assignments and people. Badge reads return counts without reconstructing a schedule. Shift-transfer approval loads its affected publication scope and conflict context, keeps the exact reviewed plan revision, and commits the sparse draft change with requests, messages, checklist reconciliation and audit atomically. The isolated workflow demo retains its compatibility path.

See [architecture](docs/architecture.md), [operations](docs/operations.md) and [local performance measurements](docs/performance-current.md) for boundaries, migration/restore checks and remaining production prerequisites. `npm run bench` exercises actual authenticated handlers with isolated 100/500-employee, 52-week fixtures. These sequential SQLite measurements do not establish Cloudflare production throughput or certify the hosting identity perimeter. The existing planner UI still bootstraps a complete compact directory catalog; account/payroll administration, shared-metadata writes, older full-instruction clients and isolated demos retain compatible full contexts. Publication sequence and lineage retain a guarded workspace metadata header, and multi-record plan commits still use a workspace revision fence. Further partitioning and measured load limits remain future work. The app still supports one workspace membership per account, company-wide planning permissions and same-day planned shifts. Department-scoped authorization, native authentication and configurable work-rule policies remain separate product work.
