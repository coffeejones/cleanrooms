# Current architecture

This document describes the implementation in this repository. It is a pilot foundation, not a measured claim of production capacity or a completed mobile backend.

## Runtime and trust boundary

The web app is hosted through Sites. Vinext builds the Cloudflare Worker, which uses the D1 `DB` binding declared in `.openai/hosting.json`. There is no PostgreSQL service or per-company deployment in this implementation.

The original visualization runs inside its preserved sandboxed iframe and CSP. `scripts/build.py` assembles `src/` into the exported `site/index.html`; the authenticated parent/bridge transports only allowlisted operations. The HTML export is a UI artifact, not a data backup.

The homepage creates one company and its owner login in a database transaction. Normal web accounts log in with their email and password. The server stores a salted password hash and a hash of each session token, and sends the session in an HttpOnly cookie. The planner binds its tab to the company verified by that session, and the first-party bridge includes that binding in API requests. The mobile API authenticates a separate employee session bound to its workspace.

Existing Sites identities and invitation links retain access through their active workspace membership. The optional private test login uses the exact existing owner membership and requires its trusted Sites identity. New companies start with a free beta plan and an empty schedule with one worksite. Repeating a registration with the same request ID and credentials returns the original company.

Roles belong to a workspace and use the shared permission catalog in `src/role-model.js`. The workspace owner and standard roles are protected. Permissions currently apply across the workspace, not individual branches or departments. Permission checks are repeated in SQL at commit using live membership and role versions.

## Data ownership

| Domain | Authoritative storage | Write boundary |
| --- | --- | --- |
| Draft series, explicit shifts/deletion state and week caches | `workspace_plan_records` + `workspace_plan_record_chunks` | Independent record versions and tombstones; dependent edits commit with one plan-generation fence |
| Published assignments and frozen site context | `workspace_published_shifts` + `workspace_publication_scopes` + `workspace_publication_chunks` | Stable occurrence identity, independent occurrence/scope versions and tombstones |
| Publication metadata and summaries | `workspace_publication_state` + `workspace_publication_records` | Versioned sequence/scope links; append-only summaries, with the latest 100 projected to the existing UI |
| Employee profiles, worksites and departments | `workspace_directory_records` + `workspace_directory_chunks` | Independent entity versions, patch commands and immutable worksite indices |
| Directory import, allocation and collection generation | `workspace_directory_state` | Source-fenced import; independent directory revision and next worksite index |
| Coverage, settings and compatibility metadata | `studio_states` + `studio_state_chunks` | Workspace metadata hash and plan-generation compare-and-swap |
| Initial plan/publication migration | `workspace_plan_imports` | One source-fenced import marker committed with every normalized child row |
| Calendar and operation read indexes | Date/parent/group/person columns and compact schedule templates on planning rows, publication `window_config`/`window_version`, `workspace_plan_window_imports` | Derived from authoritative row versions; source-fenced upgrade and version-checked repair |
| Employee calendar and workflow summaries | Compact columns on published shifts and hashed task descriptors in `workspace_published_checklist_items` | Derived from the owning published occurrence; selected older rows are repaired under source/version fences |
| Publication dependency index | `workspace_publication_links` + `workspace_publication_link_imports` | Derived from the publication state's scope links; version/token-fenced repair and atomic updates with state |
| Attendance | `workspace_time_entries` | One versioned row per occurrence; small `workspace_timekeeping` header tracks ledger revision and isolated demo metadata |
| Checklist completion | `workspace_checklist_tasks` | One row per workspace/shift/person/task; no plan revision increment |
| Offers, claims and responses | `workspace_shift_requests` | Independent request versions; active-request uniqueness |
| Shift messages and read state | `workspace_shift_messages` + `workspace_message_receipts` | Independent durable rows; read receipts never revise the plan |
| Absence requests and decisions | `workspace_absences` + `workspace_absence_imports` | Versioned request plus workspace absence revision used by dependent commits |
| Personal payroll and shared groups | `workspace_payroll` + `workspace_payroll_policies` | Separate protected versions; effective dates and immutable saved periods |
| Personal payroll revision history | `workspace_payroll_revisions` | Append-only snapshots committed with the corresponding payroll save |
| Business audit | `workspace_activity` | Append-only events committed with their business mutation |
| Workflow examples | `workspace_workflow_demo` | Isolated demo revision, never the live plan or live receipts |

JSON remains useful inside individual business records and policies; it is no longer the authoritative container for draft records, published assignments or the directory. Normalized payloads use inline data or versioned UTF-8-safe 256 KiB chunks, with byte lengths and SHA-256 verification. Large descriptions do not have a new small text cap. Draft records and full directory profiles retain a 16 MiB JSON limit; transport and compatibility-metadata limits still apply. The remaining metadata snapshot uses 512 KiB chunks and retains its 16 MiB limit. Coverage and workspace settings remain shared metadata.

An occurrence keeps the same published-row key when moved between weeks/sites or reassigned. Cancellation leaves a tombstone, and reintroduction increments its version instead of resetting it. Scope headers contain frozen location/publication metadata and occurrence ordering/digests, rather than copies of every description. Old publication summaries stay in the database beyond the UI's latest-100 window. These summaries are not a full immutable payload copy of every past publication; backups remain necessary for point-in-time recovery.

The durable activity ledger is separate from the recent recovery cache. An audit entry is not necessarily a reversible action, and neither is a substitute for database backup.

## Commands and consistency

Pure models under `src/` are shared between browser and server. Browser previews support usability; server validation and transaction guards decide what is committed.

- Current clients submit versioned `series`, `shift` and derived `week` commands. Each change carries its expected record version. The server merges an unrelated editor's changes into its latest state, but rejects a changed target, parent series or affected series-group dependency. Metadata changes also require the reviewed metadata hash. Week-cache rebasing is conservative and does not turn cached UI data into domain authority. The browser applies the server's acknowledged state while retaining later queued edits.
- Every accepted multi-record save still commits under one global plan-generation fence, with live authorization and the touched row/publication guards checked before that header changes. Per-record versions reduce unnecessary editor conflicts; they do not make the database commit independent of the global fence. Guard documents are byte-batched to stay within D1 parameter limits.
- Publication and older snapshot clients still require the exact reviewed whole-plan revision. A client reconciliation during save invalidates a prepared publication review; publishing is not silently rebased onto a different plan. The server rechecks overlap, absence, attendance and related scopes.
- Undo is a new guarded edit, not a version rollback. The activity's expected current values, affected record/dependency versions and ordinary authorization still apply. Deleted/recreated rows retain increasing versions, so returning to identical content cannot make an old command valid again.
- Employees clock using server time and cannot edit their own start/end timestamps. They can send a comment; planner corrections, rejections and reopening require reasons. Approved attendance is locked and retains the calculated payroll snapshot, so a later rate change does not recalculate the earlier approval.
- Pauses, overlaps, assignment and payroll versions are checked around attendance writes. Date/time handling currently targets Europe/Copenhagen. Planned shifts can cross midnight; the zone remains fixed. A DST transition can be clocked and closed safely; approval of an ambiguous interval requires an explicit, reasoned UTC resolution with the actual clocked pauses retained. General multi-time-zone planning remains future work.
- A planned occurrence belongs to its start date and publication week. An end time before its start time means the next calendar day; equal times are invalid. `Series.shiftInterval` and `Series.shiftDates` provide the common interval and occupied days. Conflict, absence and availability checks read bounded neighboring days without granting those rows write ownership. Ending at 00:00 does not occupy the following day.
- Net planned minutes and budgets are split across the actual civil days/weeks/months, with an unpaid planned break deducted from the end. Actual attendance still uses recorded UTC instants, explicit clock-out dates, DST resolution and frozen approval receipts. Overnight planning does not reinterpret historical approved payroll or change its work-date period ownership.
- A checklist command checks the published assignee and current template signature. Task/structure hashes are stored, with compatible signatures reconstructed for the existing UI. Different task updates do not overwrite each other. Publishing a changed template or assignee reconciles the rows atomically, so old completion cannot reappear after an undo-like template edit.
- Offers/claims remain requests until approval. Approval rechecks the published occurrence, colleague access, absence, overlap, attendance revision and request versions. A newly arriving competing claim causes a retry. The plan, publication, winning/losing request statuses, messages and checklist reconciliation then commit in one database batch.
- Messages are paged with unread priority; requests are paged with active priority. Read status comes from the durable receipts. Working-set limits bound one response/command, not a destructive history-retention rule. Closed requests and read messages stay in the database; a configurable retention/erasure policy remains to be agreed.

Legacy planning has one import transaction for all draft records, published occurrences, scopes, chunks and publication summaries. It is fenced by the source plan revision/token and finishes with `workspace_plan_imports`. An orphan normalized namespace without the shared marker fails closed; it is not silently accepted as a complete migration. Before workspace bootstrap, the trusted compatibility store can still hold the legacy snapshot. After mapping/import, reads reconstruct the same UI model from authoritative rows. A successful normalized write trims the redundant record/publication collections from the metadata snapshot.

A reconstructed read verifies payloads and rechecks the source plan generation after its queries. If a concurrent write changed that generation, it retries a bounded number of times instead of returning a mixture; persistent contention returns a retryable conflict. Corrupt payloads under an unchanged generation fail closed and are not replaced with empty data. Wire types live in `lib/planning-contracts.ts`; runtime validation remains in the shared JavaScript models and server guards.

Legacy attendance and engagement data are imported with source/version fencing before new writes use the row stores. Engagement has a one-time import marker committed atomically with its children. Snapshot PUTs cannot replace durable employee engagement with stale client arrays. Local migration fixtures exercise production SQL, not an independent permission simulator.

## Calendar read windows

Planner calendar requests use `GET /api/studio?projection=calendar&from=YYYY-MM-DD&to=YYYY-MM-DD`, with an optional continuation cursor. A window spans at most 56 valid dates and currently includes the workspace's sites; department/site filters are still applied in the UI. The server selects the workspace from authenticated membership, and display filters do not create a new authorization scope. Employee requests use the separate published-only reads described below.

The first page carries shared UI metadata and the following pages carry independently versioned draft records, compact publication headings, concrete published occurrences and calendar absence summaries. Indexed candidates include both an edited occurrence's actual date and its original anchor. Moving an occurrence out of the visible period therefore still suppresses its original series occurrence; moving it into the period loads its parent series. Published history, global publication extras and unrelated descriptions are not downloaded for this view. Checklist progress is queried only for the published occurrences on that page. Absence summaries cover every matching approved/pending request, rather than the legacy latest-hundred cache, and omit employee comments and decision reasons. Messages and requests are loaded separately when needed.

Each cursor is tied to the resolved workspace, requested period, instruction projection, plan revision/write token and absence revision. A plan or absence change invalidates the continuation with a conflict. The client collects every page before replacing its calendar model and rejects mixed generations. Deferred calendar pages allow 1,000 selected rows while operation/legacy pages retain 500; both retain the soft 1 MiB selected-payload budget. Draft geometry receipts count toward that byte budget. An individual existing long description in a full operation/legacy read can occupy an oversized page intact. The collector has a 64 MiB/50,000-record limit and asks for a shorter period if exceeded. These are working-set limits, not retention or description truncation.

Current planner reads opt into `instructions=deferred`. Selected draft schedule caches, compact published rows and historical week baselines carry an opaque instruction token and presence flag, with no description document, checklist structure or task progress. These display tokens compare note-only changes between compact and full values; they are not cryptographic write authority. Published token columns and draft schedule caches are tied to their source row version. Older selected summaries are repaired under source/version fences without advancing business versions. Large compact week baselines use SHA-256-checked 256 KiB chunks in the derived `workspace_plan_calendar_chunks` table.

`plannerDetail` requires planning authority and the exact observed plan and directory generations. It loads only selected concrete occurrences, their parent/override records and their own task progress. The browser validates source versions and instruction tokens, then upgrades its acknowledged baseline atomically without a new save ticket or changed projection. Opening, dragging, copying, replacement and group/bulk edits await this barrier before capturing their mutation; late responses cannot reopen closed editors or apply a superseded action. Large selections use bounded point batches and are adopted only when complete. Per-occurrence detail coverage keeps task progress separate from a shared series template. A failed batch preserves the previous calendar.

Compact record markers never authorize a write. The client blocks changes based on unhydrated source records, and the API rejects such markers in commands or legacy snapshots. Advisory week commands omit unloaded baseline bodies; authoritative rebasing preserves an existing baseline, and compact acknowledgments keep it out of the network payload. Selected series/publication operation records remain full while their background calendar stays compact. Legacy clients that omit the opt-in retain the full-instruction protocol.

Window objects are explicit partial projections and cannot be saved as legacy whole snapshots. A calendar window alone cannot authorize a whole-series edit or publication; those actions first load the operation-specific selection described below. Edits use expected-version commands; the server loads authoritative targets and dependencies, preserves unloaded records and acknowledges exactly its own committed rows. Independently loaded absence coverage is retained until its next window reload; an acknowledgment cannot replace it with the server's compatibility cache.

The weekly planner bootstraps one week rather than its entire eight-week visual range. `calendar-viewport.js` measures actual week intersections inside the calendar scroll container, coalesces scroll/resize work with animation frames and requests visible weeks plus one directional neighbor. Date-and-pixel anchors and measured placeholder heights preserve the position when earlier weeks change size. Disposal cancels old observers. The day list and operation screens retain their existing scoped loaders.

`planning-viewport.js` caches complete ISO-week results. The normal LRU limit is four weeks with a 64 MiB serialized-data budget; a genuinely wider visible/selected working range can retain up to eight weeks and shrinks back afterward. The adopted editable projection is exactly the requested contiguous range, not the union of disconnected cached weeks. Its merge retains source order, parent series, moved occurrences, suppressions/tombstones, publication slots and absence overlays. The plan revision, directory revision, metadata hash, absence version, workspace, viewer and capabilities must agree; mixed generations restart the requested range once before failing explicitly. Cache eviction is never a deletion command.

The persistence service coalesces missing weeks into requests of at most two ISO weeks. It can fetch one additional read-ahead week in the scroll direction, only inside the supplied eight-week UI bounds and while the normal four-week working set permits it. The server's additive `planning.recordWindows` receipt supplies absolute indexed dates, original occurrence anchors and parent identities for every returned draft version, including physical tombstones. The collector pins and validates this geometry alongside record order and versions. Complete batches split losslessly into per-week entries and insert atomically; a failed split or budget check cannot leave a partial batch cached. Required weeks remain the only adopted editable range. This uses the existing endpoint and schema without a migration.

The app serializes viewport changes. A completed response for an obsolete scroll position can warm the private cache when the page, visual period, filters, selection, editor state and active authority still match. It cannot adopt that obsolete range. Context changes cancel further page collection, and failed/incomplete reads preserve the previous model and cache. Oversized two-week collections fall back to the required individual weeks; clients with older receipts lacking typed geometry retain the single-week path. Neither path interprets omitted or evicted records as deletions.

Remounted observers restore a measurable date anchor synchronously before paint. A hidden/unmeasurable mount retains its pending date anchor across another render, while newer scroll input cancels that pending correction. Scroll direction is retained per visual context, and restoration offsets do not reverse prefetch direction. This prevents asynchronous read completion from snapping a user back to a later week or oscillating between opposite neighbors. The app can first adopt cached visible/selected weeks, then load the missing neighbor under the same busy interval and navigation/selection epoch. Its cache hint requires the current generation and complete weekly coverage, but only the normal viewport adoption grants authority. Guards are checked again between stages; failure of the neighbor leaves the already adopted visible period usable.

Routine data reconciliation, cached-visible adoption and loading completion use a persistent calendar controller. `update` retains the actual scroll element and observer for the same visual context, compares per-week presentation, and patches only changed sections or status headings. Unchanged days/cards remain connected. The app does not copy scrollTop or refocus an already active control on an unchanged scroll surface, preserving the browser's ongoing gesture. Observer patches capture the live date immediately before a synchronous DOM change and compensate only a measurable height difference above that date. Border-box week reservations prevent eviction/reload shrinkage; explicit expansion/collapse releases its reservation. Navigation/filter/zoom context changes still mount a new controller. Connected controls resolve current occurrences, groups and callbacks; detached cards, date buttons, groups and retry controls are inert. Tests exercise the actual app render/controller/observer with node identity and gesture continuity, in addition to the numeric anchor fixtures.

The app schedules six-week compact read-ahead after foreground loading settles, bounded by the existing eight-week visual period. `warmViewport` upgrades retention to at most twelve compact weeks under the unchanged 64 MiB byte budget, and collects at most two weeks per batch without using the foreground serialization lock. Retention is separate from the six-week warm target to avoid forward/backward refetch churn. There is at most one outstanding background request; a newer foreground intent, write, context change or cancellation prevents further pages and cache commits. Complete same-generation batches commit privately without adoption, reconciliation, spinner or editable versions. Partial, stale or mixed-generation responses cannot become cached authority. Byte-budget failure stops optional warming quietly, and a discovered newer generation requests an ordinary foreground refresh. The scheduler deduplicates completed windows, pauses for editors and avoids retry loops after errors/budget limits. Initial bootstrap remains one week and the legacy cache stays four weeks until warming is used.

Successful instruction hydration preserves the compact week cache. Scope reads can retain it only with a complete matching generation, including the already fenced absence revision now returned in selection receipts; missing or changed authority invalidates retention. A separate 100-selection/8 MiB detail LRU upgrades only already observed matching records, never unseen versions. Concrete occurrence/person progress snapshots have a 30-second freshness limit independent of plan revisions; hits retain their original observation time. Own checklist writes invalidate matching point entries and increment a progress epoch so older in-flight detail replies cannot restore stale completion. Oversized notes still load intact without being cached. Ordinary editor opening no longer forces a redundant fresh point read. The initial account overlay remains, while subsequent reads use card/header indicators; source-dependent scope forms keep their existing edit guards, and newer user input cancels an older opening intent.

Viewport changes flush queued saves first and cannot replace an open editor, review or newly changed selection. Late responses are checked again immediately before adoption. Only loaded weeks are expanded from shared series or used for calendar totals, baselines and mutation targets; unknown weeks show neutral placeholders and disabled actions. Base-week header labels can reuse a generation-matching read-only summary, while opening their actions obtains authoritative scope data again. Nearby moves and editor/bulk date changes load both source and target weeks before validation; series-wide and publication changes keep their complete operation-specific projections. Details, writes and explicit coverage invalidation clear incompatible private cache entries. None of these changes replaces expected-version or server conflict checks. Surviving records can keep already loaded instruction bodies only with matching canonical generation, positive record version and compact instruction/business equality; the service and UI adopt the same representation. This prevents a full-to-compact representation change alone from invalidating an in-range undo or creating a false draft write. A genuinely evicted undo target still invalidates that scoped undo instead of writing an unobserved record.

The first window after upgrade may index existing records and read legacy data once. Operational imports run before redundant snapshot collections are trimmed. The compact metadata snapshot, its new write token and the window-import marker commit atomically under the old source revision/token without advancing business record versions. Older normalized publication headings are repaired lazily for selected scopes with version/token checks. Warm window reads then avoid hydrating unrelated draft/publication payloads. Derived indexes are not a replacement source of business truth.

## Series and publication selections

The same studio endpoint accepts a normalized JSON `selection` alongside `projection=series`, `projection=series-list` or `projection=publication`. These retain the current background calendar while fetching the records needed by the open operation. Operation, tenant, plan generation and absence generation are pinned across every page. Changing the selected agreement, proposed periods, publication weeks/sites or inclusion of related scopes requires a new selection. Replaced or failed reads cannot masquerade as a complete selection.

A series selection loads every phase of the selected agreement and its manual/suppressed occurrences, including moved exceptions outside the phase dates and historical deletion versions needed for dependency checks. The catalog loads compact series/exception summaries with a description-presence flag rather than every instruction. Availability is a separate read-only set of recurrence templates, overrides/suppression state and published time-point summaries across relevant periods and all sites. It is not expanded into hundreds of copied occurrences per employee, nor merged into editable records with empty descriptions. Opening or changing an agreement loads its full source instructions and the complete dependency versions before save.

A publication selection reaches a fixed point over stored scope links, draft occurrence IDs pointing to their old published scopes, and published IDs pointing to their current effective draft locations. Replacement series IDs, reset exceptions and empty intermediate weeks remain part of that closure. It fetches full draft/published records only for that closure and the background calendar. Other-site published neighbors remain compact availability data, so conflict checks can see them without downloading their descriptions. The resulting status, change list and related scopes match the shared full publication model. Existing limits of 10,000 publication scopes and 20,000 scope links remain explicit limits; a dependency closure is never silently truncated.

Normalized link rows are an index of the authoritative publication metadata, not a second editable graph. A cold repair reads that metadata once and rebuilds the index under its own version/write token; a losing repair cannot mark a different generation ready. A publication-state change updates the graph and its marker in the existing atomic plan transaction. Schedule summaries are likewise derived from the owning record version. Warm selections do not need unrelated instruction chunks or global publication-history payloads.

## Targeted authoritative commands

Modern saves opt into the targeted command path with `commandReceipt:'records'` and `metadataChanged:false`, whether the browser holds a partial selection or a complete planning cache. It resolves live membership and shared metadata, then reads changed records, parent series, and every member/exception/tombstone required by the original group dependencies. An unrelated edit can be retried under the new global generation while retaining the original expected record versions and dependency tokens. A changed target, parent or group still rejects. Compatibility checks for retained weekday times, group IDs and planned pauses apply to the affected records. Drafts may contain overlaps or absence warnings; publication is the enforcement boundary for those planning conflicts.

Publication uses the authoritative dependency closure and full payloads for its selected assignments, with compact published neighbors for cross-site conflict checks. It still requires the exact immutable global revision the planner reviewed, even when a subsequent edit is unrelated. The server checks actual approved absence, attendance locks and live permissions, then fences their dependent versions in the same commit. Checklist cleanup, messages, publication rows, draft changes and audit events share that commit. The selected occurrence keeps its stable identity and version history. A scoped preview or client-supplied workspace/person selector never replaces these checks.

Warm command writes do not reconstruct the background calendar, hydrate the global engagement projection, or read unrelated instruction chunks/publication history for their acknowledgments. Recent compatibility activity is archived into the durable ledger and removed from the metadata cache by the first successful targeted commit; later commands append only their own events. Initial legacy imports, index/summary repair and that retained activity cache are cold-path work. Clients without the receipt opt-in, actual shared-metadata edits and isolated demo sessions retain the compatibility path, which can still reconstruct the complete plan. An older partial client continues to receive its replacement-style acknowledgment.

The targeted response is a `recordPatch` acknowledgment: exactly committed draft rows and their versions, the original projection when present, and a refresh flag. The browser applies it to the exact submitted snapshot, keeps untouched observed values/versions, and then preserves later queued local edits. It never adopts an unseen peer record's version. Since this path does not replace shared metadata, it echoes the client's original metadata hash; a later metadata edit based on stale data must still conflict. Derived week caches can remain local rather than requiring unrelated baseline payloads. Series changes in a partial cache, rebased saves and publication invalidate coverage; the same selector then requires a fresh read, and publication requires another review before confirmation. A complete cache's own non-rebased record changes do not require a replacement read. A patch acknowledgment is not a claim that the browser now holds every record from the new global revision.

## Employee and organization records

`POST /api/directory` provides paged compact catalogs, point reads and versioned entity patches. Ordinary employee edits and department/worksite changes update their own rows and the independent directory generation, with audit and live permission/reference guards in the same transaction. They do not increment the plan revision. Unknown server profile fields survive patches to the current editable fields. Employees are archived through their status rather than physically deleted; worksite indices remain stable because existing shifts refer to them. A new worksite and its department can be created atomically, and a concurrent index allocation rejects instead of remapping references.

Planner bootstrap still includes the complete compact identity catalog needed by the existing lists, filters and pickers. Its current seven employee fields are list data, while full profiles and future extra fields are read by identity before editing. The planning response's directory receipt supplies entity versions without duplicating those aliases. The browser keeps this cache separate from editable planning metadata and does not send the roster or organization with a plan command. Point reads and exact own-write acknowledgments update only observed entities; they cannot certify that an unseen rest of the catalog matches a newer directory generation. Catalog collection is paged, generation-fenced and replaced atomically; profile caching is bounded.

Planning windows pin the directory generation across their pages. Publication uses the directory revision from the actual reviewed planning context, rather than a newer head seen by a point edit. A directory change therefore cannot silently replace the names, assignment references or frozen worksite context used by an older review. The compatibility read/write adapter reconstructs the old roster/organization shape and converts guarded legacy edits into directory-row changes. The first directory import preserves full profiles before trimming their redundant snapshot copies; an incomplete import fails closed.

## Operational period and person reads

The ordinary Hours and Absence pages use their fixed account operations without first expanding the calendar cache into the complete company plan. Attendance reads select the requested period and, for an employee or employee preview, the selected identity. The weekly overview receives draft planned-minute totals after planned pauses, separately from compact published schedules used to review registrations. It enriches these totals from the compact directory catalog and retains active people with zero planned hours. A newer directory generation requires a generation-matching compact catalog refresh; a page of relevant identities cannot certify that the rest of the roster is current.

Attendance pages pin the plan, directory and attendance-ledger revisions. The client retains the first page's schedules, planned totals and demo context while collecting registrations. A changed generation restarts collection once; persistent conflict or failure exposes no partial collection. A superseded period cannot overwrite a newer one. The client bounds a collection at 50,000 registrations or 64 MiB of UTF-8 response data and reports an explicit failure rather than silently truncating it. This is a working-set limit, not retention. A forgotten running registration remains reachable for its employee even outside the visible month. Existing employee clock permissions, approval locks, reason requirements and isolated time demonstrations remain separate from editable planning data.

Absence uses server filters, authoritative counts and one displayed page at a time. Responses include names only for the relevant identities. The browser keeps the displayed requests' own versions for decisions, rather than reusing an older calendar status or accumulating all queried historical requests in calendar state. Cursor continuations are scoped to the tenant, person, filters, absence generation and directory generation. A stale continuation restarts at the first page once, with the same filters and consistent pagination labels. Successful real absence mutations invalidate the calendar coverage so returning to planning reloads its independent absence summaries. The isolated planning demo continues to use its local fixtures and decisions.

## Employee calendar and workflow reads

`employeeRead` selects published occurrences for one employee and at most 56 dates. An employee is bound to their authenticated person; the person selector is available only to planners previewing an employee. Responses contain compact schedules, frozen location context, instruction-presence and checklist completion totals, without instruction bodies or full task structure. The first page also supplies the next upcoming published shift independently of the visible period. Initial non-planner `/api/studio` bootstrap uses this same bounded projection and the person's own absence requests rather than reconstructing a company plan.

The employee collector pins plan and directory generations across pages, adopts a complete window atomically, bounds its working set at 50,000 records/64 MiB, and ignores superseded navigation. The separate `employeeShift` point operation checks the current assignee and published occurrence before returning one intact instruction/template and its progress. The browser retains one selected detail, cancels late detail responses on close or navigation, and never uses a partial calendar row as editable template authority. Checklist writes resolve that same concrete assignment on the server and return only its progress. Frozen site records preserve stable numeric indices while the wire location list remains compact.

`workflowRead` pages messages, requests, own/open shifts and eligible colleagues independently. Message/request pages carry tenant/filter/directory and relevant revision guards; the browser rejects mixed generations rather than merging stale pages. Count-only `summary:true` reads do not load schedules, full profiles or instruction payloads. Normal workflow context reads compact candidate schedules and point-loads referenced assignments and identities. Long employee comments remain intact within explicit byte budgets, and unread/active history remains accessible through continuations.

Shift-transfer approval loads the selected publication scope and compact conflict neighbors, then writes the affected draft occurrence with sparse expected versions. It retains the exact reviewed global plan revision, live membership/role guards, current request/assignee checks, absence and attendance fencing, and atomic request/message/checklist/audit effects. The persistence layer keeps the reviewed request-list revision separate from calendar and badge refreshes. Global publication metadata and an affected scope remain part of this approval boundary; the isolated workflow demo and one-time legacy imports retain their explicit full-context paths.

## Capacity and remaining boundaries

Normalization removes the earlier 2 MB company-ledger failure and repeated per-registration payroll fetches, and prevents each draft/publication save from replacing an authoritative company-plan blob. It does not certify a number of concurrent users or million-employee capacity. D1 limits, request/response sizes, large policies, global commit contention and client rendering still need workload-specific tests.

Planner calendar/details, series-editor/catalog, publication-review reads, ordinary record commands, directory entity reads/writes, attendance period/person operations, absence queries/decisions, employee calendars/details and workflow reads are targeted. Compatibility paths, workspace-metadata writes, account/payroll administration and isolated demos can still reconstruct a complete planning model. The current planner UI also collects a complete compact identity catalog; paging the endpoint does not make its existing all-person list virtualized. A large number of calendar events and long operation selections can still exceed response, worker-memory or rendering budgets, particularly during a compatibility write or the first upgrade. [Local route measurements](performance-current.md) document 100/500-person year fixtures; they are sequential SQLite measurements, not a production capacity or concurrency claim. History endpoints already provide pagination; clients must preserve it rather than accumulating unlimited pages.

There is one D1 binding today. Database-per-tenant or database-group routing, a larger relational service, queues for notification fan-out/export, native push, general idempotency keys and replica/session routing are future choices driven by measured traffic. They are not already configured capabilities.

The client still contains a large DOM application and layered CSS assembled in a fixed build order. Most JavaScript domain code is not fully covered by TypeScript checking.
